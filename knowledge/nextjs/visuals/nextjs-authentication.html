The critical loop

Login成功はDashboard表示の直前ではない

  1. 1authorize()がUserを返す
  2. 2NextAuthがSession / Cookieを作る
  3. 3BrowserへRedirectを返す
  4. 4Browserが新しいGET Requestを送る
  5. 5proxy.tsとauthorized()が再実行

この「新しいRequest」がAuthenticationとAuthorizationをつなぐ。

02

End-to-end flows

Requestを追えば迷わない

色は実行境界を示します。横へ追うと「誰が次を呼ぶか」と「どこで新しいRequestになるか」が見えます。

未ログインで /dashboard/invoices へ

matcherは認証要否ではなく、Proxyを実行するRequestかを選びます。

  1. ClientGET /dashboardBrowserが保護Pageを要求
  2. Next.jsmatcherProxy対象のRequestか選ぶ
  3. Proxyproxy.tsNextAuth(...).authを実行
  4. Auth.jsSession確認Cookie / JWTを処理
  5. Callbackauthorized()auth.userなし → false
  6. ResponseRedirect /logincallbackUrlに元の目的地

Login成功 → Session → 新しいRequest

Authentication成功後、Sessionを持った次のRequestでAuthorizationが成功します。

  1. ClientForm submitemail・password・redirectTo
  2. React / Serverauthenticate()useActionStateが呼び出す
  3. Auth.jssignIn()credentials Providerを選択
  4. Providerauthorize()Zodで入力を検証
  5. DatabasegetUser()PostgreSQLからUser取得
  6. Serverbcrypt.compare()plain passwordとhashを比較
  7. Auth.jsSession / CookieUserを認証状態へ変換
  8. ClientRedirectBrowserがcallbackUrlへ移動
  9. New requestproxy → authorized今度はauth.userあり
境界：Redirect後は同じ処理の続きではなく、Browserから始まる新しいHTTP Request。

Login失敗 → Error stateへ戻る

authorize()のnullはCredentialsSigninとなり、Server Actionが画面向け文字列へ変換します。

  1. ClientForm submit誤ったcredential
  2. Server Actionauthenticate()signIn()へ渡す
  3. Providerauthorize()Userなし / password不一致
  4. Auth.jsCredentialsSigninAuthErrorとしてthrow
  5. Server Actioncatch AuthError"Invalid credentials."を返す
  6. ReactuseActionStateError messageを再描画
03

Who calls whom?

Fileではなく、呼び出し鎖を見る

短いframework codeの裏には、Next.js・React・Auth.jsが生成する呼び出しがあります。

Page protection chain

HTTP RequestからAuthorization decisionまで。

  1. Next.jsがproxy.tsを見つける
  2. matcherがProxy対象を選ぶ
  3. NextAuth(authConfig).authがSessionを読む
  4. Auth.jsがauthorized({ auth, request })を呼ぶ
  5. boolean / RedirectをNextAuthがResponseへ反映

Login chain

Form submitからAuthentication decisionまで。

  1. Reactがauthenticate(prevState, formData)を呼ぶ
  2. Server ActionがsignIn("credentials", formData)を呼ぶ
  3. Auth.jsがCredentials Providerを選ぶ
  4. Providerがauthorize(credentials)を呼ぶ
  5. 結果をSession処理またはAuthErrorへつなぐ
Next.js invokesproxy.ts — file conventionによる入口
React invokesauthenticate() — useActionState / form action
Auth.js invokesauthorized()とauthorize() — 異なる段階

Critical code only

短いCodeを展開する

ここでの展開はmental modelのための概念表現で、library内部実装そのものではありません。

Proxy handler Next.js + Auth.js
const configuredAuth = NextAuth(authConfig);
const authHandler = configuredAuth.auth;
export default authHandler;

HTTP Requestを受け、Session確認とauthorized()へつなぐ。

Destructuring JavaScript syntax
authorized(data) {
  const auth = data.auth;
  const nextUrl = data.request.nextUrl;
}

request: { nextUrl }はNextAuth専用構文ではなく分割代入。

Credentials sign-in Server Action
await signIn('credentials', formData);

Providerを選び、FormDataのcredentialとredirect先をAuth.jsへ渡す。

Password check Runtime
await bcrypt.compare(
  plainPassword,
  storedHash
);

保存用hashの生成ではなく、入力された平文と既存hashの照合。

06

Self-check

流れを再構成できるか？

Questionを開く前に、自分の言葉で説明してみる。

matcherとauthorized()は何を判断する？

matcherはProxyを実行するRequestか、authorized()は現在の認証情報でそのURLへ通すかを判断する。

authorize()を実際に呼ぶのは誰？

signIn("credentials")で選ばれたCredentials Providerを通じてAuth.js / NextAuthが呼ぶ。

なぜLogin成功後にproxy.tsが再実行される？

RedirectによりBrowserがcallbackUrlへ新しいHTTP Requestを送るため。そのRequestはSession Cookieを持つ。

return userからauth.userまでに何がある？

Auth.jsの認証成功判断、Session / JWT / Cookie処理、Redirect、後続RequestでのSession読み取りがある。

TypeScript型とZodの差は？

TypeScript型はcompile-timeの支援。Zodは実行時の値を検証する。

callbackUrlとredirectToはどうつながる？

Login URLのcallbackUrlを画面が読み、hidden inputのredirectToとしてFormDataへ入れ、成功時の移動先としてAuth.jsへ渡す。
