React data hook

usePracticeData

46行。fetchの結果をReactへ渡すだけの小さなhookだが、 競合する応答の破棄、再取得中も画面を空にしない、 書き込みの後に全一覧を取り直すの3つを引き受けている。 その3つがどう実現されているかを図で追う。

00

Overview

全体像

登場人物は4つ。画面（View）、hook、repository、そしてrepositoryの中にある module-levelの購読リスト。hookはこの真ん中に座り、両側からの合図で動く。

Why it exists

なぜ生のuseEffectを毎回書かないのか

このhookが無いと、6か所の呼び出しすべてで「useStateを2つ置き、useEffectで fetchし、cancel flagを立て、書き込み後の取り直しを購読する」を書き写すことになる。 写し間違いが起きるのはたいていcancel flagと購読の解除で、 どちらも症状が出るのが遅い（古い結果が一瞬出る、離れた画面が更新されない）。

もう1つの目的は差し替えの一点化。localStorage版からDB版へ移したとき、 repositoryの中身は全部書き換わったが、このhookと呼び出し側は変えていない。

01

State

3つのstate

dataとloadingは画面に出る値。nonceは出ない値で、 「もう一度effectを走らせる」ためだけに存在する。

state 1

data

T | null。初期値はnull。取得が成功したときだけ入れ替わる。

nullの意味
まだ一度も成功していない（取得中、または失敗した）
失敗時
nullのまま。前回の成功値があればそれを保つ
state 2

loading

初期値true。最初の決着（成功でも失敗でも）でfalseになり、二度とtrueへ戻らない。

意味
「まだ1件も描けない」であって「通信中」ではない
用途
スケルトンを出すか、実物を出すかの分岐
state 3

nonce

ただの整数カウンタ。値そのものは誰も読まない。reload()が1増やす。

なぜ必要
effectはdepsが変わったときしか走らない。depsが同じままで再実行させる唯一の手が、依存に入れた数を動かすこと
別名
refresh key、reload token と呼ばれる定番の型
i reloadは毎renderで作り直さない。 useCallback(..., [])で固定してあるので、effect 2（購読）の依存[reload]が動かず、 購読と解除はmount時とunmount時の各1回だけになる。ここを固定し忘れると、 renderのたびに購読し直す。

02

Effect 1

取得と、古い応答の破棄

hookの心臓。load()を呼び、返ってきたらstateへ入れる。 ただし「返ってきた時点でまだ自分が最新か」を必ず確かめる。 

useEffect(() => {
  let cancelled = false;
  load()
    .then((value) => {
      if (!cancelled) { setData(value); setLoading(false); }
    })
    .catch(() => {
      if (!cancelled) setLoading(false);
    });
  return () => { cancelled = true; };  // 次のrunの直前に呼ばれる
}, [...deps, nonce]);
! これはfetchのabortではない。 通信自体は最後まで走り、応答も届く。捨てているのは結果の採用だけ。 通信を本当に止めるならAbortControllerをload側へ渡す設計が要る。 現状は「requestが軽く、捨てるコストのほうが安い」という判断。

03

One-way flag

loadingは片道

再取得のたびにsetLoading(true)へ戻す実装が普通だが、このhookは戻さない。 意図的な選択で、代償もある。

狙い

条件を変えても画面が空にならない

Discoverでタグを1つ足すたびにloadingがtrueへ戻ると、 そのたび一覧がスケルトンに置き換わって画面が点滅する。 前の結果を出したまま差し替えれば、視線の位置が動かない。

副次的に、effectの中で同期的にsetStateを呼ばずに済んでいる。 load()より前にsetLoading(true)を置くと、 React 19のStrict Modeでの二重実行と噛み合わせが悪い。

代償

2回目以降は「取得中」が見えない

スケルトンが出るのはその画面で最初の1回だけ。 以降は古い結果が出たまま、いつの間にか新しい結果へ入れ替わる。 通信が遅いと「押したのに何も起きない」ように見える。

必要になったらisRefreshingのような2つ目のflagを足し、 一覧に薄い被せを出すのが素直な拡張。loadingの意味は変えない。

! 失敗してもloadingはfalseになる。 catchが握りつぶすので、hookは失敗を呼び出し側へ伝えない。 呼び出し側でdata === nullを「取得中」と読むと、失敗時に永久スケルトンになる。 分岐は必ずloadingで書く。

04

Effect 2

書き込みの通知

いいねを押した瞬間、押した場所だけでなくその画面のすべての一覧が取り直される。 仕組みはReactの外にある1つのSet。

store側

repository.ts

const listeners = new Set<() => void>();

export function subscribeProblemSets(l) {
  listeners.add(l);
  return () => { listeners.delete(l); };  // 解除関数を返す
}

function notify() {
  for (const l of listeners) l();
}
hook側

use-practice-data.ts

useEffect(
  () => subscribeProblemSets(reload),
  [reload],
);

subscribeProblemSetsが返す解除関数を、effectの戻り値へそのまま流している。 Reactはeffectの戻り値をcleanupとして扱うので、unmount時に自動で解除される。 1行で購読と後始末の両方が済んでいる。

性質

粗いが、間違えようがない

どのhookが何のqueryを持っているかは見ていない。全員に「取り直せ」と言うだけ。 無駄なrequestは出るが（Discoverなら1回のいいねで3本）、 「更新したのに一覧が古いまま」は構造的に起きない。

境界

tabをまたがない

listenersはJavaScript moduleのtop-levelにある変数。 同じtabの中でしか共有されない。別tabや別端末の変更は届かない。 越えるにはBroadcastChannel、polling、SSEのいずれかが要る。

05

Contract

depsの約束

このhookで唯一「使う側が守らないと壊れる」のがここ。 eslint-disableが1行入っているのは、その責任を呼び出し側へ移したという印。

なぜdisableするのか

lintはloadの中身を追えない

loadは呼び出し側で作られた関数で、その中でどの変数を読むかはhookから見えない。 react-hooks/exhaustive-depsは[...deps, nonce]のような spreadを含む依存配列を検査できないので、警告を出すしかない。 そこで検査を切り、代わりに「loadが読む値は呼び出し側がdepsへ全部書く」という約束にした。 

// discover-view.tsx —— queryはuseMemoで固定してから渡す
const query = useMemo<DiscoverQuery>(
  () => ({ q: keyword, tags, bands, sort, … }),
  [keyword, tags, bands, sort],
);

const results = usePracticeData(() => repo.discover(query), [query]);
const fresh   = usePracticeData(() => repo.featured("new"), []);
効いていない引数

loadはdepsに入っていない

() => repo.discover(query)は毎renderで新しい関数になるが、 依存配列は[...deps, nonce]だけなので再取得の引き金にはならない。 引き金はdepsとnonceのみ。

だからqueryをuseMemoで固定する必要がある。 毎render新しいobjectだと[query]が毎回変わり、取得が止まらなくなる。

失敗の形

2種類しかない

書き忘れ
loadが読む値をdepsに入れ忘れる → 古い値で取り続ける（stale closure）
入れすぎ
毎render変わる値を入れる → 無限に取得し続ける

どちらもlintが黙っているので、レビューでdepsとloadを並べて読むのが唯一の防御。

07

Scope

やらないこと

46行に収めるために落とした機能。どれも「必要になったら足す」で、 今のところ必要になっていない。

no cache

共有も重複排除もない

hookのinstanceごとに独立してrequestを出す。同じqueryを2か所で使えば2本飛ぶ。 Discoverは初回に3本。

no error

失敗を外へ出さない

catchが握りつぶすので、呼び出し側は「失敗した」と「0件だった」を区別できない。 区別が要る画面が出たらerrorを戻り値へ足す。

no retry

再試行しない

一度失敗したら、depsが変わるかnotify()が来るまでそのまま。 画面の再読み込みが実質的な復帰手段。

no suspense

Suspenseに参加しない

useEffectで取るので、React SuspenseもNext.jsのloading.tsxもこの待ち時間を見られない。 スケルトンはloadingを見て自前で出している。

no abort

通信を止めない

捨てるのは結果だけ。requestは最後まで走る（02節）。

置き換えるなら

移行先

cacheとerrorが同時に要るようになったらTanStack QueryかSWR。 サーバ側で取れる画面が増えたら、Server Component + use()へ寄せて このhookの担当範囲を狭める。
